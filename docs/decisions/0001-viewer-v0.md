# ADR-0001: ビューワー v0 の骨格

状態: 採用 (2026-07-23)。決定2 (vendor + sync-core) は ADR-0002 で置き換え済み。本文は当時の名 (IFCXS) のまま残す — 歴史の記録。

## 文脈

IFCXS本体は「オーサリングツールは作らない」(writing-architecture) を保ちながら、M1-2 でケイパビリティを可視化する道具立てを求めている (MUN-143 / MUN-144)。最低限のビューワー — 読み込み、平面、レベルの重ね (2.5D)、Spaceの三次元可視化と用途の色分け、面積集計 — を最初に立てる。将来は若干のオーサリング (壁の位置をずらす、別の通り芯へ再アサイン程度) がGUIで欲しくなる見込み。

## 決定

**1. three.js 直、ThatOpen は今は使わない。** ThatOpen (components/fragments) はIFCのロード・フラグメント管理・BIMツール群が主戦場。IFCXSのジオメトリは生成物であり (空間の押し出しと境界由来の壁 — 数百メッシュ)、シーン・カメラ・ピッキングは three 直の方が薄い。ThatOpen は IFC 取り込み (M5) でIFCコーパスを読む段になったら導入する — 本体roadmapの「BIM/IFC系ツールはThatOpenのOSS」はその局面の話。

**2. コアは vendor + sync-core。** parse/model/graph/check/light/plan を `src/core/` へコピーし、`npm run sync-core` で本体から追随する。file:依存は本体のpackage構成 (private・エクスポート無し) に手を入れさせ、submoduleは日々の书き味が重い。壁線分の導出 (segmentsFor) や面積 (areaM2) を二重実装しないことが本体との答えの一致 (テストで114空間・316境界を検算) を保証する。coreは手で編集しない。乖離したら本体を直してから同期する。

**3. ビルドは常に単一HTML。** MUN-143の「一つのファイルとして閲覧」を、配布形態そのものにする (vite-plugin-singlefile)。`index.html` の `<script id="ifcxs-embed">` が埋め込みポイントで、CLI (`npm run embed`) でもビューワーUI内 (書き出し→配布用HTML) でもモデル入りの単一ファイルが作れる。ビューワー自身が自分の素のHTMLを複製して埋め込む — ビルドが一つしかないことの帰結。

**4. オーサリングv0はエディタペインそのもの。** 原本はソーステキストであり、ビューは全て導出物。エディタで一行直せば平面も立体も面積表も即座に変わる — これが「テキストが原本」の実演。将来のGUIオーサリング (壁をドラッグ→オフセット書き換え、通り芯の再アサイン) も、モデルを直接触らず**テキストへの編集操作として**実装する。ストアが source を唯一の状態として持つのはこの布石。選択・ホバー・経路などビューワー状態はテキストに入れない。

**5. 描画規約は core/plan.ts と同一。** 平面ビューは svgPlan の移植 (mm座標・y反転のみ) で、CLIが吐くSVGと同じ図が画面に出る。作図の語彙 (壁芯・扉の軌跡・吹抜けの対角線・数えない分節の淡い面) を二つ持たない。

## 代替案

- ThatOpen componentsベース: IFCロード機構が現時点で不要、抽象の層が厚い。見送り。
- 正準JSONの読み込み対応: author形式がDSLである以上、v0はDSLのみ読む。JSONは書き出しのみ。取り込みが要る局面 (レイヤー合成) で `fromCanonical` を書く。
- CADライクな編集UI: 作らない。本体の「オーサリングツール作らない」を守り、編集はテキスト経由に限る。

## 帰結

ビューワーはIFCXSの「答え」を持たない — 全てcoreの関数の呼び出しであり、記法が進化したら sync-core と例の追加だけで追随する。エディタ+即時再生成の構えは、法規クエリ (M2) の結果表示やレイヤー合成の可視化をこの上に足せる形にしている。
