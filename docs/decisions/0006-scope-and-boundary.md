# ADR-0006 (ugatsu): 範囲を文書にし、意味を作るのをやめる

日付: 2026-07-27 / 状態: 採用 (v0.4) / 前提: koyu [spec/scope.md](https://github.com/kensnzk/koyu/blob/main/spec/scope.md) §1・§6・§8、koyu [docs/policy.md](https://github.com/kensnzk/koyu/blob/main/docs/policy.md) §7・§13

## 文脈

koyu が 1.0.0 へ向けて三つの領域 (core / 検証 / 表現) を分け、ugatsu は「表現」の側として名指しで置かれた。方針が ugatsu に与えた立ち位置は一行である。

> **koyu は座標を作らない。ugatsu は意味を作らない。**

そして ugatsu 1.0.0 が凍結する面は四つだけと定められた — 入力・導出の一致・配布の形・**範囲の明示**。図面の精度は凍結の対象ではなく、要求は「上げていける形になっていること」だけである。

四つのうち、いま最も欠けているのが**範囲の明示**だった。何を描き何を描かないかがどこにも書かれていなかったので、**描画側の限界が記述側の限界として原本に持ち込まれる**筋が開いていた。図に出ないものは書けないもののように見え、原本が表現に引きずられる。

そして片側で、ugatsu は**意味を作ってしまっていた**。`src/lib/stats.ts` の延べ面積は「吹抜け以外はすべて床」と数えていた。koyu には `isIndoor` という「延べ面積を問う三箇所の唯一の答え」があり (koyu ADR-0028)、そちらは外部 (`type:exterior`) と半屋外 (外部に `open`/`air:1` で接する空間) を屋内床面積から外す。**同じ原本に対して二つの答えが出ていた。**

| 例 | ugatsu の合計 | `koyu stats` の合計 | 差 |
|---|---|---|---|
| complex | 32,342.24㎡ | 31,606.24㎡ | 736.00㎡ (屋外) |
| twin | 172,893.68㎡ | 141,448.56㎡ | 31,445.12㎡ (屋外 24,911.04 + 半屋外 6,534.08) |
| tower | 5,727.08㎡ | 4,785.92㎡ | 941.16㎡ (半屋外) |
| house | 165.99㎡ | 92.75㎡ | 73.24㎡ (半屋外) |

しかも ugatsu の内部でも割れていた。インスペクタの敷地表は `siteReport.totalFloor` を出しており、これは `isIndoor` を使う。**同じ画面の二箇所が違う延べ面積を出していた。**

加えて三つ。配布HTMLに版が一つも埋まっておらず、**利用者が「どの版の形を見ているか」を言えなかった**。`setRouteTarget` を呼ぶ箇所がゼロで、経路の状態と三つのビューのハイライトが**到達不能なまま在った**。診断は `check(model)` の文字列を正規表現で解き直していた。

## 決定

**1. `docs/scope.md` を範囲の規範として置く。**

何を描くか (六つの面と、各要素の出所)、何を描かないか、何を判定しないか、埋めている既定値、読める版、追随が要る箇所。**列挙は実装を読んで作り、同梱の例で件数を数えた** — 推測で書けば、書かれていない限界が新しい限界になる。

「何を描かないか」は二つに割った。**muro に書けるのに ugatsu が描かないもの** (上部吹抜けの投影・垂直の境界・斜め線分の上の開口・採光・道路・自由語の大半) と、**そもそも持たない図** (寸法線・縮尺・勾配屋根・断面・立面)。前者が本題である — **描けないことは、書けないことではない**と言うためには、書けるのに描けていないものの名前が要る。

既定値の表は独立の節にした。**これは危険な層である** — 仮定した数で描いた図と、書かれた数で描いた図が画面の上で区別できない。とくに空間の押し出し高さ 2400mm は、koyu が `SUF01` (error) で「形を作らない」と決めた場面で ugatsu が形を作ってしまう箇所であり、**check が赤いのに立体は完成して見える**。表に載せた。

**2. 面積の母集団は koyu の `isIndoor` に一致させる。**

「なぜ違う数を出すのか」を書いて残す選択もあったが、採らなかった。**差の原因が表現ではなく判断だったからである。**寸法線の有無や線の太さは表現であり、ugatsu が自由に決めてよい。「その空間を延べ面積に数えるか」は判断であり、原本と core が既に答えている。表現の自由を口実に判断を持てば、それは意味を作ることである。

区分は四つ (屋内 / 吹抜け / 屋外 / 半屋外) に名前を付けて表に出し、**算入するのは屋内だけ**にした。屋外と半屋外は数として別に立てる — 消すのではない。数は原本にあり、算入するかどうかだけが koyu の答えである。半屋外の算入条件は法規細部であり、**ugatsu も koyu も決めない**。

ついでに敷地ゾーン (`site:1`) をゾーン別の表から外した。専有面積の言葉では常に 0 になる行であり、`koyu stats` も出さない。

テストで四点を縛った。四例すべてで表の合計が `isIndoor` の合計に一致すること。区分が `isIndoor` と厳密に一致すること。complex と twin の実数。そして**延べ面積が `siteReport.totalFloor` と一致すること** — 同じ問いに二つの答えを持たない、を機械で守る。

**3. 版を三本、配布物に刻む。**

`<meta name="ugatsu:version">` / `<meta name="koyu:version">` / `<meta name="muro:version">` を `transformIndexHtml` で注入し、画面はツールバー左端 (hover で三本すべて) とインスペクタの概要に出す。meta は React のマウント前から在るので、自己埋め込みの配布HTML (`exportEmbeddedHtml` が写す素のHTML) にもそのまま残る。

**koyu の版は `package.json` の範囲指定 (`^0.15.0`) ではなく、実際に解決された実体から読む。**範囲を刻めば、ローカルへリンクしているとき (ADR-0005) に埋め込んだ版が嘘になる。muro の版は koyu が実行時に名乗る `DEFAULT_LANGUAGE_VERSION` を読む — 直書きすれば版が上がったときに黙って嘘になる。

**4. `setRouteTarget` は消さずに実装する。**

到達不能な面を残さないという規律 (koyu policy §11-8) に対して、選択肢は実装か削除の二つだった。**実装を採ったのは、消す側の代償が大きいからである。**経路のハイライトは平面・3D・面積表の三面に既に書かれており、削除は三面から機能を削ることになる。そして動線は koyu が `doorsBetween` で答える問いであり、**ugatsu はその答えを塗るだけ** — この形は「意味を作らない」の実例そのものである。

インスペクタに行き先の `Select` を置いた。行き先の母集団は書かれた空間そのもので、絞り込みの意味を ugatsu が作らない。到達できないときは「接する空間の既定は壁であり、扉は書かなければ無い」と言う — 到達不能は**判定ではなく事実**であり、`validate` の `access.unreachable` とは層が違う。

**5. `checkDiagnostics` への移行は次の版へ送る。**

`@kensnzk/koyu` の版を上げない (1.0.0-rc.1 は未公開) という制約の中で、`checkDiagnostics` は 0.15.0 にも既に在る。それでも今回は移らなかった。移行は診断の**提示**の作り直し (コード表示・`related` への飛び先・severity の由来) を伴い、範囲の明示という本題と混ざる。`docs/scope.md` §7 に、追随が要る箇所として `derive()` `validate` `daylightInputs` と並べて列挙した — **列挙が済んでいれば、送るのは先延ばしではなく順序である。**

## 代替案

**面積の差を「そういう仕様」として文書化する。** 一行で済み、コードを触らない。棄却したのは、それが**表現の自由と判断の自由を混同する**から。ugatsu が延べ面積の母集団を持てるなら、次は用途の定義も、通行の定義も持てることになり、「意味を作らない」が空文になる。そして画面の中で `siteReport.totalFloor` と割れたままになる — **同じ画面が二つの延べ面積を出す状態**を仕様と呼ぶことはできない。

**`stats.ts` を捨てて koyu の集計をそのまま呼ぶ。** koyu には CLI の `stats` があるが、`console.log` へ書くだけで構造を返さない。返すようにするのは koyu 側の変更であり、いまは触れない。`isIndoor` は既に公開されているので、母集団の判断だけを借りて表の組み立てを ugatsu が持つ形で足りる — **判断を借り、表現を持つ**が正しい分担である。

**`setRouteTarget` と経路のハイライトを削除する。** 使われていない面を残さない、には最も忠実で、差分は小さい。棄却したのは、動線が ugatsu の役割 (koyu の答えを見せる) の中心にあるから。**使われていないことは、要らないことではない** — 要らないなら三面のハイライトが書かれた理由が説明できない。

**版を `package.json` の依存範囲から刻む。** ビルド時に `node_modules` を読まずに済む。棄却理由は決定3のとおり — 範囲は実体ではなく、ローカルリンク中に嘘をつく。

**`docs/scope.md` を README に畳む。** 読まれる確率は上がる。棄却したのは、README が「触ってもらう」ための頁 (ADR-0004) であり、規範を混ぜると両方が薄まるから。koyu が spec と guide を分けている理由と同じである。

## 帰結と代償

**得たもの。** 描画側の限界が原本へ逆流する筋が閉じた。`docs/scope.md` に列挙がある限り、「ugatsu に出ないから書けない」という推論は成り立たない。延べ面積は koyu と一致し、画面の中の二箇所も一致した。配布された一枚のHTMLが、自分がどの版の形を見せているかを名乗れるようになった。到達不能な面が一つ減った。

**代償1: 面積表の数が変わる。** 過去に書き出した CSV と数が合わない。合わないのが正しい — 以前の数が `koyu stats` と食い違っていた。CSV には「区分」列を足し、行ごとに算入したかどうかが読めるようにした。

**代償2: 既定値の表は、直さない限り古びる。** `buildScene.ts:383` のような行番号つきの表は、コードが動けばずれる。行番号を書いたのは**探せることのほうが大事**だからで、ずれても対象と値で辿れる。既定値を足すときは表も足す、が規律になる。

**代償3: 「描かない」の列挙は、直したら消す作業を生む。** 上部吹抜けの投影を描くようになったら、表から消さなければならない。消し忘れれば文書が嘘をつく。**これは正しい代償である** — 嘘をつく可能性が生まれるのは、そこに約束が立ったからである。

**代償4: 版を三本名乗ることは、三本が別々に動くことを認めることでもある。** 一本にまとめたほうが利用者には易しいが、まとめられない。muro 0.5 を読む ugatsu 0.4.0 が koyu 0.15.0 で描いている、という状態が事実であり、**事実より易しい名乗りは嘘である**。

**まだない。** 機械形式 (正準JSON) の読み込み — 凍結面「入力」はここが欠けている。`derive(model): Form` を呼ぶ形 — これが立つまで凍結面「導出の一致」は検査しようがない (koyu roadmap)。`validate` の提示。`checkDiagnostics` への移行。上部吹抜けの投影と、斜め線分の上の開口。
